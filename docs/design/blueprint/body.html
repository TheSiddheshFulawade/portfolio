Systems, and how they fail

Two systems built around one question: what is still true after something fails? Run a simulation, inject a failure, and read the evidence.

PayFlow

In development

A payment moves through three services that each own their database. No distributed transaction joins them, so the design has to make every step safe to repeat, every step before capture compensable, and every payment end in one terminal state. Reserve, risk check and capture are merged and tested per service. Compensation and the recovery sweeper are specified and not built yet; chaos tests follow.

  • No message without its state change, no second effect

    State and outgoing message commit in one transaction (outbox). Consumers record the message id with the effect (inbox), so a redelivery has no second effect.

  • Money is held before it moves

    Funds are reserved, risk is checked, then the hold is captured. Compensation is always a release of the hold (specified, not built yet), so REVERSED is an authorisation reversal: any hold was released and nothing was captured.

  • Every payment ends in one state

    Specified, not built yet: a sweeper re-sends overdue commands up to 3 times, then compensates. A release is retried until the wallet confirms it; if the money was already captured, the wallet says so and the payment ends COMPLETED.

    Settlement Lab

    Engine measured, API built but not deployed

    Transfers pass a bounded queue, workers post them to an in-memory ledger, and each posting is published to a simulated general ledger through a retry inside a circuit breaker; what cannot be delivered waits in an in-memory outbox. Settlement here means posting transfers in the project's own in-memory ledger. No real money moves and no settlement finality is claimed. Six invariants are asserted after every run.

          From the repository, not from the simulation above.

          One run, results committed 19 Nov 2026 (3eb119a): cloud container, Intel Xeon at 2.10 GHz, 4 cores, Linux, JDK 21.0.13. 100,000 submissions per row from 64 closed-loop clients through 8 workers; 10,000 accounts; 20% of transfers within 20 hot accounts; 2,006 duplicates and 802 to 853 rejections per row. Rates are submissions answered by the engine; delivery to the simulated general ledger is not in the rate and finishes afterwards. Ordered locking answered 2.9× to 4.6× as many submissions per second as CAS; virtual threads had the lower p99 and the higher p50 in all six pairs.
